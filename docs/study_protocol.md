# SceneLens User Study Protocol

이 문서는 실험 진행 프로토콜의 작업본이다. 논문 8장(User Study)과 용어를 맞춘다.
- 수정 위치는 로그 기반 3범주(**단일 컷 / 컷 사이 / 장면**). "beyond-panel edit ratio"는 쓰지 않는다.
- 문제의 "수준"은 코딩하지 않는다 (관점마다 다르게 봄 → 코더 신뢰도 낮음).
- 관객 읽기에서 감독은 `revise/retain/defer` 버튼을 누르지 않는다. 시스템이 컷의 목적과 읽힌 것을 대조해 **어긋난 자리**를 보여 주고, 이후 고쳤는지/그대로 뒀는지가 로그(`intent_check` → 뒤따른 `edit`)로 관찰된다.
- 감독에게 되묻는 단계는 없다. 관객 읽기는 의도를 모르는 상태로 읽는 것이 원칙이라, 답을 받아도 그 읽기에 되먹일 수 없다.
- 생성 후 검토에는 서사 관점이 참여하지 않는다 (서사는 생성 전 계획 단계).

---

## 1. Participants

**확정**
- 영상 제작 경험 있음
- storyboard novice
- formative study와 동일한 target population
- within-subjects (두 조건 모두 수행)

**미정**
- 최종 N — 정성 중심이므로 12–16 범위에서 결정 (표준). pilot 뒤 확정.

---

## 2. Tasks / Story Materials

**Story A/B는 연구자가 미리 작성하고 pilot으로 검증한 짧은 대본 2개.** 시나리오 저작은 이 연구의 범위가 아니며, 참가자가 직접 쓰면 이야기 난이도가 통제되지 않고 시간도 그쪽에 쏠린다.

각 대본을 아래 템플릿으로 동일하게 만든다.

**주는 것 (Background)**
- 인물 2명과 관계
- 현재 상황
- 기본 공간 1~2곳
- 반드시 일어나는 핵심 사건 3개
- 90–120초 분량
- 공간 2곳 이상 사용

**주지 않는 것**
- 구체적인 대사
- 인물의 세부 감정
- 사건을 관객이 어떻게 해석해야 하는지
- 정확한 정보 공개 시점
- 구체적인 장소 디자인
- shot / camera / blocking
- 컷 수와 순서
- 편집 방식

**예시 (Story 뼈대)**
> A와 B는 한동안 만나지 않았던 가까운 사이이다.
> A가 B를 만나기 위해 찾아온다.
> A는 B가 자신을 피하고 있다는 단서를 발견한다.
> 두 사람은 결국 마주친다.
> 장면에는 두 개 이상의 공간을 사용한다.

**task 설계 근거.** SceneLens에서 서사 관점도(생성 전 계획 단계에서) 검토되므로, CineVision처럼 완성된 dialogue script를 주면 너무 많이 정해주는 편이다. 반대로 StoryDiffusion의 concept ideation처럼 "이 주제로 이야기를 만드세요"라고만 하면 story writing 능력 차이가 커진다. **사건의 뼈대는 통제하되, 그 사건의 의미·정보 공개·시각적 표현·컷 구성은 참가자에게 남긴다.**

**두 대본의 동등성.** 인물 2명 이상, 공간 2곳 이상, 컷 사이 관계를 고려해야 하는 사건, 인물의 정보 상태·목표 변화, 연출 여지가 열려 있을 것. story × 도구는 counterbalancing.

## 3. Timing

| 단계 | 시간 |
| --- | --- |
| 연구 소개 / 기본 설문 | 5분 |
| 두 도구 Tutorial | 10분 |
| **Condition 1 제작** | **20분** |
| Post-task Review | 5분 |
| Post-condition Questionnaire | 3분 |
| **Condition 2 제작** | **20분** |
| Post-task Review | 5분 |
| Post-condition Questionnaire | 3분 |
| Final Comparative Interview | 15분 |
| **합계** | **약 86분** |

> **[pilot 확인]** 90–120초 장면을 생성하고 검토·수정까지 20분이 충분한지. 부족하면 대본을 더 짧게 하거나 시간을 늘린다. 두 조건 시간은 반드시 동일.

### 3.1 로그 운영 (실험자용)

로그는 브라우저에 쌓이고 참가자에게는 보이지 않는다. **측정 구간은 실험자가 명시적으로 연다** — 누르지 않으면 그 조건은 측정되지 않으므로, 아래 순서를 조건마다 그대로 따른다.

모든 조작은 **화면 오른쪽 아래의 점**을 눌러 여는 로그 창에서 버튼으로 할 수 있다. 단축키는 같은 것을 부르는 지름길이다. 점의 색이 곧 상태다 — **노랑(깜빡임) = 아직 측정 전**, **초록 = 측정 중**, 회색 = 종료됨.

| 시점 | 조작 | 왜 |
| --- | --- | --- |
| 조건 시작 전 | URL에 `?condition=<baseline\|scenelens>&order=<1\|2>`, 또는 로그 창 머리글의 조건·순서 칸을 눌러 입력 | 조건과 **몇 번째인지**를 이벤트마다 붙인다. within-subjects라 순서 효과를 조건 차이와 갈라야 한다 |
| Tutorial 동안 | **아무것도 안 누름** | 이때 쌓이는 것은 `phase: tutorial`로 기록만 되고 측정에서 빠진다 |
| Tutorial 끝, 제작 시작 직전 | 로그 창의 **`과제 시작`** (또는 Ctrl+Shift+S) | 여기부터가 측정 구간이다. 오른쪽 아래 점이 초록으로 바뀐다 |
| 20분 종료 | 로그 창의 **`과제 종료`** (또는 Ctrl+Shift+S) | 이후 실험자가 화면을 정리하며 누른 것이 측정에 섞이지 않는다 |
| 조건 종료 후 | 로그 창의 **`내보내기 (파일 + 서버)`** (또는 Ctrl+Shift+E) | 파일로 받고 Supabase에도 올린다. 결과를 창으로 알린다. 반드시 비우기 전에 |
| 다음 조건 전 | 로그 창의 **`비우기`** (또는 Ctrl+Shift+R) | 세션·조건·로그를 지운다. 되돌릴 수 없으므로 내보낸 뒤에만 |

### 3.2 로그 저장소 (Supabase) 설정

내보내기는 **두 곳**으로 나간다 — 실험자 컴퓨터에 JSON 파일, 그리고 Supabase의 `study_sessions` 테이블. 서버(Render)는 중계만 하므로 재배포·재시작과 무관하다.

**한 번만 하면 되는 설정:**

1. Supabase 프로젝트의 SQL Editor에서 테이블을 만든다.

   ```sql
   create table study_sessions (
     id             bigserial primary key,
     created_at     timestamptz not null default now(),
     tool           text not null,
     participant_id text,
     condition      text,
     story_id       text,
     payload        jsonb not null
   );

   -- 정책을 만들지 않는다. service_role만 RLS를 우회하므로,
   -- 키가 새더라도 익명으로는 읽히지 않는다.
   alter table study_sessions enable row level security;
   ```

2. Render 대시보드 → 서비스 → Environment에 두 개를 넣는다.

   | Key | 값 |
   | --- | --- |
   | `SUPABASE_URL` | `https://<프로젝트ref>.supabase.co` |
   | `SUPABASE_SECRET_KEY` | Settings → API의 **Secret API key** (`sb_secret_...`) 또는 `service_role` JWT (`eyJ...`). 둘 다 된다. **anon / publishable 키는 안 된다** — RLS에 막힌다. |

**확인.** Ctrl+Shift+L로 로그 창을 열었을 때 빨간 `서버 저장 불가` 줄이 없으면 저장이 되는 상태다. 있으면 그 줄이 이유를 말한다(환경변수 누락 / 테이블 없음 / 연결 실패). 이 줄이 보이면 **실험을 시작하기 전에** 고친다 — 그대로 진행하면 그 참가자 기록은 다운로드 파일 하나에만 남는다.

내보낼 때(Ctrl+Shift+E)도 성공·실패를 창으로 알린다. 실패해도 파일은 이미 받았으므로, 그 JSON을 보관하면 나중에 넣을 수 있다.

---

**확인 방법.** Ctrl+Shift+L로 로그 창을 열면 맨 위 띠가 현재 상태를 말한다 — 노란색 `튜토리얼 (측정 안 함)`이면 아직 안 눌린 것이고, 초록색 `과제 진행 중`이면 측정 중이다. 시작을 깜빡했더라도 그 기록은 지워지지 않고 `tutorial`로 남으므로, 내보낸 JSON의 `summary.tutorial.events`가 비정상적으로 크면 그 세션은 시점을 되짚어 복구할 수 있다.

## 4. Participant Instructions & Tutorial Protocol

### 4.1 공통 과제 안내

참가자는 제공된 이야기 소재를 바탕으로 약 90–120초 분량의 장면을 스토리보드로 제작한다.

이야기 소재에는 등장인물, 기본 상황, 반드시 포함되어야 하는 핵심 사건이 제공된다. 참가자는 이야기의 뼈대는 유지하되, 세부적인 연출 방식은 자유롭게 결정한다.

자유롭게 결정할 수 있는 요소:
- 인물의 구체적인 행동과 감정
- 공간의 세부적인 설정과 배치
- 어떤 정보를 언제 보여줄지
- 카메라의 거리, 각도, 시점
- 컷의 수와 순서
- 컷 사이의 연결 방식
- 대사 및 세부적인 표현 방식

각 조건에서 **20분**의 제작 시간을 제공한다 (두 조건 동일).

과제의 목적은 완성도 높은 최종 이미지를 만드는 것이 아니라, 주어진 시간 안에서 참가자가 중요하다고 생각하는 연출 결정을 내리고 스토리보드를 구성하는 것이다.

### 4.2 Think-aloud 안내

두 조건 모두에서 참가자는 작업 중 자신의 생각을 자연스럽게 말하도록 요청받는다.

> 작업하면서 지금 무엇을 보고 있는지, 어떤 부분이 마음에 들거나 들지 않는지, 무엇을 바꾸려고 하는지 가능한 한 소리 내어 말씀해주세요. 정답을 설명할 필요는 없으며, 평소 머릿속으로 생각할 내용을 자연스럽게 말씀해주시면 됩니다.

장시간 말이 없으면 중립 prompt만 사용한다.

> 지금 어떤 생각을 하고 계신지 말씀해주실 수 있을까요?

특정 연출 문제나 기능 사용을 유도하는 질문은 작업 중 하지 않는다.

### 4.3 Tutorial (공통)

본 과제 전, 각 도구의 기본 사용법을 익히는 짧은 tutorial. 본 실험과 다른 간단한 이야기 소재를 쓴다. 두 조건 비슷한 시간. 연구자는 **기능 사용법만 설명하고 좋은 스토리보드의 기준이나 연출 전략은 가르치지 않는다.**

### 4.4 Baseline Tutorial

Storyboarder.ai 조건에서 필요한 기본 기능을 설명한다.
- 스토리보드 생성
- 패널 확인
- 프롬프트 / 내용 수정
- 패널 재생성
- 컷 추가 및 삭제

각 기능의 사용법만 설명한다. 다음 연출적 조언은 하지 않는다.
- 어떤 컷이 필요한지
- 어떤 카메라 구도를 써야 하는지
- 컷 사이 관계를 어떻게 검토해야 하는지
- 어떤 정보가 관객에게 전달되어야 하는지

### 4.5 SceneLens Tutorial

먼저 기본 생성·편집 방법을 설명한다. 추가로 SceneLens가 연출 결정을 여러 관점과 범위에서 검토하도록 지원한다는 것을 안내한다.

#### 연출 관점 (Directorial Lenses)

**계획 단계 (생성 전)와 검토 단계 (생성 후)를 구분해 안내한다.**

- **생성 전 계획 (컷 계획 단계):** 서사·미장센·촬영·편집 네 관점이 이야기와 컷 계획을 글로만 미리 점검한다.
  - **서사:** 사건의 단계, 정보가 드러나는 순서
  - **미장센:** 인물·공간·소품의 배치와 동선
  - **촬영:** 카메라 커버리지
  - **편집:** 컷 구성, 컷 사이 관계
- **생성 후 검토 (검토 화면):** 미장센·촬영·편집 **세 관점**이 만들어진 스토리보드를 분석한다. 서사는 이 단계에 참여하지 않는다 (컷 구성은 그리기 전에 정해지므로).

이 관점들은 스토리보드를 검토하기 위한 서로 다른 시각이며, 모든 관점을 다 써야 하는 것은 아니다.

시스템의 진단은 정답이 아니라 **참고할 수 있는 제안·판단 근거**임을 명확히 한다.

> 시스템이 제시하는 내용은 반드시 따라야 하는 정답이 아닙니다. 필요하다고 생각되는 내용만 참고하고, 동의하지 않으면 그대로 유지하거나 다른 방식으로 수정할 수 있습니다.

#### 수정 범위 (Editing Scope)

개별 요소뿐 아니라 컷의 추가·삭제·구성, 컷 사이의 관계, 장면 전체 기준 등 서로 다른 범위에서 수정할 수 있음을 **기능 설명 수준에서만** 안내한다. 특정 상황에서 어떤 범위를 써야 하는지는 설명하지 않는다.

#### 관객 읽기 (Viewer)

현재 스토리보드를 의도를 모르는 관객의 관점에서 읽었을 때 가능한 해석을 보여주는 기능이라고 설명한다.

> 관객 읽기는 현재 스토리보드가 관객에게 어떻게 읽힐 수 있는지를 보여줍니다. 이 결과 역시 정답이나 반드시 수정해야 하는 문제를 뜻하지 않습니다.

읽기가 끝나면 시스템이 각 컷의 목적과 실제로 읽힌 것을 대조해 **의도와 다르게 읽힌 자리**를 표시한다는 것도 안내한다. 참가자에게 따로 답을 적게 하지는 않는다. 관객 읽기의 사용은 **자유롭게 둔다.** 특정 시점에 쓰도록 요구하거나, 사용 후 반드시 수정하도록 요청하지 않는다.

### 4.6 연구자가 유도하지 않아야 하는 것

실험 중 다음 지시를 하지 않는다.
- "서사 관점도 확인해보세요."
- "네 가지 관점을 모두 사용해보세요."
- "컷 사이의 관계도 수정해보세요."
- "이건 패널이 아니라 장면 수준의 문제입니다."
- "관객 읽기를 한번 확인해보세요."
- "관객이 다르게 해석했으니 수정해야 할 것 같습니다."

기능 사용법 질문에는 답하되, **어떤 연출 판단을 내려야 하는지에는 개입하지 않는다.**

### 4.7 조건 종료

20분이 지나면 작업 상태와 관계없이 제작을 종료한다. 참가자에게 모든 문제를 해결하거나 모든 기능을 써야 할 필요는 없다고 사전에 안내한다. 종료 후 Post-task Review와 Questionnaire를 진행한 뒤 다음 조건으로 이동한다.

### 4.8 핵심 통제 원칙

두 조건에서 **이야기 소재, 제작 시간, think-aloud 요구, 과제 목표는 동일하게 유지한다.** 조건 간 차이는 도구가 제공하는 지원 방식에만 두며, 연구자가 SceneLens의 설계 의도에 맞는 행동을 직접 유도하지 않는다. SceneLens의 관점·수정 범위·관객 읽기는 **무엇을 할 수 있는지**만 설명하고, **언제·왜 써야 하는지**는 참가자가 스스로 판단하게 한다.

## 5. Analysis Plan

각 RQ는 두 종류의 증거로 답한다. 소절마다 어느 쪽인지 밝힌다.
- **조건 간 비교** — 두 조건에 공통인 측정(재생성·삽입·삭제 지표, 수정 위치 분포, CSI, 공통 문항, 두 조건에 같은 프레임으로 코딩한 정성 지표)을 baseline vs SceneLens로 비교. within-subjects이므로 비모수 검정(Wilcoxon signed-rank), 도구 순서 확인.
- **사용 패턴 기술 (descriptive)** — SceneLens에만 있는 scaffolding(관점 검토·판단 근거·수정 방향·관점 관계·관객 읽기, 그리고 합치기·이음새·장면 기준)이 실제 작업에서 어떻게 쓰였는지. baseline에 대응이 없으므로 조건 비교가 아니라 mechanism evidence로 본다.

**해석 원칙.**
- 컷 사이·장면 수정이 많을수록 좋다고 보지 않는다. 장면에 구조 문제가 적으면 낮은 게 정상이다. 수정 위치 분포는 "SceneLens에서 더 많다 = 낫다"가 아니라 분포 자체의 차이로 본다.
- 관점별 수정 빈도 차이도 SceneLens가 관점을 UI로 제공하기 때문이므로 성능 지표로 쓰지 않는다.
- 관객 읽기가 실제 인간 관객과 얼마나 일치하는지는 이 연구의 범위가 아니다.

### 5.1 RQ1 — Problem Recognition and Reflection

정량적인 문제 개수보다 **think-aloud와 인터뷰 중심으로 정성 분석**한다.

- 이전에 고려하지 않았던 문제를 새롭게 인식한 사례
- 문제를 바라보는 기준이 달라진 사례
- 네 관점이 판단에 영향을 준 방식
- 인식한 문제가 어떤 관점과 관련되는가 (**problem perspective** 코딩: narrative / mise-en-scène / cinematography / editing)
- 새롭게 인식한 문제가 실제 수정으로 이어진 사례
- 문제를 인식했지만 수정하지 않은 이유 (인터뷰)

수정 로그는 정성적 발견이 실제 행동으로 이어졌는지 확인하는 보조 자료.

**코딩.** 각 problem episode에 perspective와 reflection trigger(self-initiated / lens-prompted / viewer-reading)를 코딩한다. 문제의 "수준"은 코딩하지 않는다 — 같은 현상을 관점마다 다르게 볼 수 있어 코더 신뢰도가 낮다. 코더 2명, perspective·trigger에 대해 κ 보고.

### 5.2 RQ2 — Scope of Intervention

두 조건의 수정 행동을 **로그 기반** 3범주로 비교한다.

**수정 위치 (로그로 결정 — 코더 판단 아님)**
- **단일 컷** — 프롬프트 수정 / 샷 값 조정 / 그림 위 덧그리기
- **컷 사이** — 이음새 조작 (넣기·합치기·삭제·순서)
- **장면** — 장면 기준 수정

각 범주의 수정 수·비율을 조건 간 비교.

**재생성 의존도**
- 전체 패널 재생성 횟수
- 동일 패널 반복 재생성 횟수
- 전체 수정 중 재생성 비율

**공통 편집 기능 (조건 비교)**
- 컷 삽입·삭제 횟수 — 두 도구 모두 있음
- 컷 삽입 완수율 (넣기만 하고 안 채운 것 제외) — SceneLens는 AI 제안이 붙으므로 완수율 차이도 본다

**SceneLens 전용 (mechanism, 조건 비교 아님)**
- 컷 합치기, 이음새 명시(연결 방식·경과 시간), 장면 기준 수정을 언제·왜 썼는가
- baseline에서 개별 컷을 넘어선 문제를 언급한 episode에 참가자가 무엇을 했는지 정성으로 병치

보는 것은 **분포의 차이** — baseline에서 단일 컷에 몰리던 수정이 SceneLens에서 컷 사이·장면으로도 갔는지, 그리고 그 계기가 무엇이었는지 (대표 episode). (해석 원칙은 §5 참조.)

### 5.3 RQ3 — Viewer-Oriented Reflection

관객 읽기는 baseline에 대응 기능이 없으므로 **SceneLens-only mechanism analysis**.

- 관객 읽기 사용 시점·횟수
- 의도 대조가 어긋난 자리를 몇 개 냈는지, 그중 어느 컷을 열어 봤는지 (`intent_check`의 `off`·`offPanels`)
- 어긋난 자리를 받은 뒤 연출 검토 재실행이나 수정으로 이어졌는지
- 재검토 이후 어느 위치(단일 컷 / 컷 사이 / 장면)를 고쳤는지
- 해석 차이를 보고 판단 방향이 바뀐 사례
- 갈린 것을 확인했지만 그대로 두거나 미룬 이유 (인터뷰)

사용 빈도 자체를 성과로 해석하지 않는다. 핵심은 관객 관점이 **실제 재검토와 수정으로 어떻게 연결되었는가**이다.

관객 읽기가 실제 인간 관객의 해석과 얼마나 일치하는지는 이 연구의 범위가 아니다. 이 도구는 그런 일치를 주장하지 않고 감독의 재검토를 유도하는 성찰 장치이므로, 우리가 보는 것은 예측 정확도가 아니라 재검토가 실제로 일어났는지다.

### 5.4 SceneLens Mechanism Analysis

SceneLens 조건에서만 제공되는 scaffolding의 사용 패턴.
- 관점(렌즈) 검토 실행, 추가 관점 호출
- 판단 근거(criterion·visual evidence·theory) 조회
- 수정 방향(alternatives) 선택·수정
- 관점 사이 관계 조회
- 관객 읽기 사용
- 각 scaffolding 사용 이후 발생한 수정

baseline과의 성능 비교가 아니라, Comparative Analysis에서 나타난 작업 방식 변화를 **SceneLens의 어떤 지원이 만들어냈는지 설명하는 보조 근거.**

### 5.5 Creative Support Experience

두 조건에서 동일하게 실시한 Selected CSI와 custom questionnaire 비교.

**Selected CSI** — Exploration / Expressiveness / Results Worth Effort (기존 문항·scoring 사용)

**Custom Ratings** — 무엇을 수정할지 판단하기 쉬웠는가 / 패널을 넘어 관계·구조를 수정할 수 있었는가 / 관객 관점에서 검토할 수 있었는가 / 연출 결정을 통제하고 있다고 느꼈는가

behavioral outcome을 대체하는 것이 아니라 보완하는 secondary measure.

### 5.6 Overall Analysis Structure

| Evidence | 분석 목적 |
| --- | --- |
| Think-aloud / Interview | 새롭게 무엇을 보게 되었고 판단 기준이 어떻게 달라졌는지 |
| Edit logs | 어느 위치(단일 컷 / 컷 사이 / 장면)에서 수정했는지 |
| Regeneration logs | 패널 재생성에 얼마나 의존했는지 |
| SceneLens interaction logs | 어떤 scaffolding이 실제 작업에 쓰였는지 |
| Video + think-aloud coding | problem perspective, reflection trigger |
| Selected CSI / Custom ratings | 창작 지원 경험과 주관적 차이 |

평가의 핵심은 단일 성능 점수를 만드는 것이 아니라, **SceneLens가 문제 인식, 수정 범위, 관객 관점을 활용한 재검토 과정을 어떻게 변화시키는지를 서로 다른 형태의 evidence로 확인하는 것**이다.

## 6. Post-task Review — 각 조건 직후 5분

각 condition 종료 직후, 방금 작업에서 나타난 **구체적인 판단·수정 episode를 짧게 회고**한다. 일반적 만족도가 아니라, **무엇을 새롭게 인식했고, 판단이 어떻게 변했으며, 그것이 어떤 행동으로 이어졌는지**를 작업 직후의 기억으로 확보한다.

**공통 질문**
- "여기서 한동안 이 부분을 보셨는데 무엇을 확인하고 있었나요?"
- "이 내용을 보기 전에는 이 부분을 어떻게 생각하고 있었나요?"
- "이걸 본 뒤 판단이 달라졌나요?"
- "왜 수정했나요 / 왜 그대로 두었나요?"

### Episode A — Problem Recognition

**대상 예시**
- 관점이나 판단 근거를 확인한 뒤 이전에 언급하지 않았던 문제를 새롭게 이야기한 순간
- 스토리보드를 바라보는 판단 기준이 달라진 순간
- 정보 흐름, 프레이밍, 컷 사이 관계 등 이전에 고려하지 않던 요소를 새롭게 검토한 순간

**질문**
1. 이 시점에서 어떤 부분을 보고 있었고, 무엇을 생각하고 있었나요?
2. 이 부분은 이전부터 중요하다고 생각한 건가요, 아니면 작업하면서 새롭게 고려하게 된 건가요?
3. 무엇이 이 부분을 다시 보게 만들었나요?
4. 그 판단 이후 실제로 수정했나요? 수정하지 않았다면 왜 그대로 두었나요?

### Episode B — Scope of Intervention

**대상 예시**
- 개별 패널 수정이나 재생성을 하다가 컷 구성·컷 사이·장면 구조 수정으로 이동한 순간
- 패널 수준의 수정만으로는 해결하기 어렵다고 판단한 순간
- 이음새 조작, 컷 추가·삭제, 장면 기준 수정 등을 고려하거나 수행한 순간

**질문**
1. 처음에는 이 부분을 어떤 방식으로 수정하려고 했나요?
2. 왜 그 방법만으로는 충분하지 않다고 생각했나요?
3. 이후 어떤 범위를 수정해야 한다고 판단했나요?
4. 다른 수정 방법도 고려했나요? 최종적으로 이 방법을 선택한 이유는?

### Episode C — Viewer-Oriented Reflection

**대상 예시**
- 관객 읽기를 확인한 뒤 자신의 기존 판단을 다시 검토한 순간
- 예상과 다른 해석을 확인한 순간
- 의도와 다르게 읽힌 자리를 확인한 뒤, 고치거나 / 그대로 두거나 / 나중으로 미룬 순간

**질문**
1. 관객 읽기에서 무엇이 가장 눈에 들어왔나요?
2. 이 결과를 보기 전에는 해당 부분을 어떻게 생각하고 있었나요?
3. 관객 읽기를 본 뒤 자신의 판단이 달라진 부분이 있었나요?
4. 이후 왜 고쳤나요 / 왜 그대로 두었나요 / 왜 나중으로 미뤘나요?
5. 이 읽기가 유용하지 않거나 동의하기 어려웠던 부분도 있었나요?

### 공통 Neutral Probes (필요할 때만)
- 그때 무엇을 보고 그렇게 생각했나요?
- 그전에는 어떻게 생각하고 있었나요?
- 무엇 때문에 판단이 달라졌나요?
- 그 판단이 다음 행동에 어떤 영향을 주었나요?
- 수정하지 않았다면 그 이유는 무엇인가요?

### 운영 원칙
- 이미 think-aloud에서 충분히 설명한 내용은 반복해 묻지 않는다.
- 연구자가 특정 관점·범위·관객 결과가 중요했다고 암시하지 않는다.
- 세 episode 유형을 **모두 억지로 확보하지 않는다.**
- 한 condition당 가장 의미 있는 episode 1–2개를 중심으로 짧게.
- 구체적 episode는 condition 직후 회수하고, 두 도구의 전체적 차이와 종합 해석은 Final Comparative Interview에서.

## 7. Post-condition Questionnaire

각 문항 1–7점 (1 = 전혀 그렇지 않다 / 7 = 매우 그렇다). 공통 문항 4개 + CSI.

**판단 (Judgment)**
1. 이 도구를 사용하면서 스토리보드에서 **무엇을 검토해야 할지 판단하기 쉬웠다.**

**수정 (Intervention)**
2. 내가 검토가 필요하다고 느낀 부분에 대해 **어떻게 수정할지 판단하기 쉬웠다.**
3. 개별 패널뿐 아니라 **컷 사이의 관계나 장면 구조까지 수정할 수 있다고 느꼈다.**

**관객 관점 (Audience-oriented reflection)**
4. 스토리보드가 **내 의도를 모르는 사람에게 어떻게 읽힐지 검토할 수 있었다.**

**통제감 (Agency)**
5. 스토리보드의 연출 방향을 **내가 통제하고 있다고 느꼈다.**

**Selected CSI** — Exploration / Expressiveness / Results Worth Effort (기존 문항·scoring 절차 사용)

---

## 8. Final Comparative Interview — 두 조건 종료 후 15분

**진행 원칙**
- 먼저 참가자가 **자신의 언어로 두 도구의 차이**를 설명하게 한다.
- 이후 연구 질문 관련 내용을 순차적으로 probe한다.
- narrative / mise-en-scène / cinematography / editing 등 연구자 용어는 가능한 한 먼저 제시하지 않는다.
- 이미 충분히 설명한 내용은 반복 질문하지 않는다.
- 하위 probe는 필요할 때만.

**Open-ended comparison**
- 두 도구를 사용한 경험에서 가장 크게 달랐던 점은 무엇인가요?

**Problem Recognition and Reflection**
- 각 도구에서 스토리보드를 검토할 때 주로 무엇을 보고 판단했나요?
- 한 도구에서는 생각하지 않았지만 다른 도구에서는 고려하게 된 부분이 있었나요?

**Scope of Intervention**
- 각 도구에서 주로 어떤 방식으로 스토리보드를 수정했나요?
- 개별 패널을 수정하는 것만으로는 해결하기 어렵다고 느낀 순간이 있었나요?

**Viewer-Oriented Reflection**
- SceneLens의 관객 읽기를 봤을 때 어떠셨나요? Storyboarder.ai로 작업할 때도 비슷한 생각을 하셨나요?
- (사용했다면) 그 결과를 어떻게 받아들였나요?

**SceneLens Mechanism**
- SceneLens의 관점이나 질문을 작업 중 어떻게 활용했나요?
- SceneLens가 보여준 수정 방향이나 관점 사이 관계를 사용했다면, 자신의 선택에 어떤 영향을 주었나요?

**Agency and Overall Experience**
- 두 도구 중 어느 쪽에서 자신이 연출 결정을 더 주도적으로 내리고 있다고 느꼈나요? 왜 그렇게 느꼈나요?
- SceneLens에서 유지하고 싶은 지원과 제거하거나 바꾸고 싶은 지원이 있다면 무엇인가요?
- 지금까지 이야기하지 않았지만 두 도구를 쓰면서 중요하다고 느낀 차이가 있나요?

**핵심:** 먼저 참가자가 자신의 언어로 차이를 말하게 하고 → 그다음 우리가 관심 있는 관점 / 수정 범위 / 관객 읽기를 probe한다.

### 2026-08-31 — 로그를 프로토콜에 맞춤

읽기 갈림 기능을 걷어내고 의도 대조로 바꾼 뒤, 로그가 이 문서의 측정과 어긋나 있던 것을 고쳤다.

- **읽기 갈림 → 의도 대조.** 감독이 갈린 자리에 답을 적는 단계가 없어졌다. 시스템이 컷의 목적과 읽힌 것을 대조해 어긋난 자리를 보여 주고, 그 뒤 고쳤는지가 관찰된다. 4.5·5.3·Episode C의 관련 문구를 고쳤다.
- **`장면` 범주가 늘 0이었다.** `sequence` 층위를 남기는 곳이 코드에 없었다. 장면 기준 수정(fact 설정·구간·씬 override)을 그 자리로 잡았다.
- **컷 삽입·삭제가 비대칭이었다.** 경로에 따라 `seam`/`shot`으로 갈리고 일부는 로그가 없었다. 컷 수가 바뀌는 일이므로 넷 다 `shot`으로 모았다.
- **`intent_check` 이벤트 추가.** 어긋난 컷 수·자리와 그 뒤 첫 수정을 남긴다. 이것이 없으면 "고칠 게 없어서 안 고쳤다"와 "보고도 안 고쳤다"가 갈리지 않는다.
- **`order`(몇 번째 조건) 추가.** within-subjects의 순서 효과를 조건 차이와 가른다.
- **측정 구간을 명시적으로 연다 (§3.1).** 전에는 첫 이벤트가 곧 세션 시작이라 튜토리얼이 과제에 섞였다. 이제 `과제 시작`을 눌러야 측정이 시작되고, 그 전 기록은 지우지 않고 `phase: tutorial`로 남는다.
