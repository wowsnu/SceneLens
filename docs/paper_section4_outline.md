작성: 2026-08-30. 목적: 논문 4장을 CHI 시스템 논문 형식으로 쓸 때의 순서와
각 문단이 담을 것. 완성 원고가 아니라 골격이다.

**쓰기 원칙**
- 코드 파일명, 함수명, 한국어 UI 라벨, "어느 버튼" 같은 건 원고에 넣지 않는다.

## 4.1 Design Goals (짧게, 이미 formative에서 도출됨)

- 한 문단: formative의 DR1–DR3를 SceneLens의 설계 방향 DG1–DG3로 옮긴다고 선언.
- DG1 / DG2 / DG3 각각 2–3문장. (지금 논문.md 4.1의 내용이 재료. bullet을
  문단으로 풀 것.)
- 표 하나: DG — 묻는 것 — 대응 DR. (한 줄 요약)

**DG1.** 생성 전과 후에 걸쳐 연출 결정을 검토 가능하게 만든다.
**DG2.** 문제가 있는 수준(컷 안 / 컷 / 컷 사이 / 장면)에서 개입하게 한다.
**DG3.** 감독의 의도와 독립된 바깥 읽기로 스토리보드를 되돌아보게 한다.

## 4.2 System Overview (한 문단 + Fig 3)

- 워크플로우를 한 문단으로: 이야기 입력 → AI가 씬·비트·컷으로 구조화 →
  감독이 컷 계획 검토 → 러프 스토리보드 생성 → 렌즈로 검토 → 문제 수준에서
  수정 → 의도 없는 관객 읽기로 되돌아봄 → 필요하면 반복.
- 여기서 강조할 것: 이 흐름은 **선형이 아니라 순환**이다. 관객 읽기에서
  나온 것이 다시 렌즈 검토로 돌아간다.
- Fig 3 = 전체 워크플로우 (실제 화면 스크린샷 모자이크). 이후 Fig 4–8이
  각 단계 확대.

## 4.3 연출 결정을 계획하고 검토하기 (DG1)

### 4.3.1 네 관점 (framing 문단)

- 우리는 연출 결정을 narrative, mise-en-scène, cinematography, editing
  네 관점으로 정리한다.
- **왜 이 넷인가** — 영화 이론에서 서로 다른 연출 결정을 설명하는 주요
  범주와 대응 [Bordwell/Thompson/Smith 등]. formative에서 참가자들이 실제로
  쓴 판단도 반복적으로 이 넷으로 나뉘었다 (F1/DR1).
- **완전한 taxonomy가 아니다.** 초보자가 무엇을 기준으로 볼지 조직하기 위한
  실용적 관점이다. 하나의 결정이 여러 관점에 걸칠 수 있다.
- **네 관점이 같은 때·같은 자리에서 일하지 않는다.** narrative는 주로
  생성 전 계획을, 나머지 셋은 생성 후 화면 분석을 맡는다. (이유는 4.3.2/4.3.3)

### 4.3.2 생성 전 — 정하려는 결정 꺼내 놓기 (Fig 4)

- AI가 이야기를 씬·비트로 나누고 각 비트를 컷으로 쪼갠다. 컷의 역할과
  정보 흐름도 함께 계획한다. → 실제 줄콘티/shot planning 관행과 연결
  [줄콘티 관련 근거].
- 계획은 글(표)로 외부화된다. **아직 안 정한 것은 "미정"으로 명시적으로
  남는다** — 빈칸을 억지로 채우지 않는다. (DG1: 생성 전에 결정 공간을
  보이게 만든다.)
- 이 단계에서 네 관점이 이미지 없이 계획만 훑는다. 화면 근거가 없으므로
  프레이밍·연속성은 아직 보지 않고, 배치·커버리지·컷 구성 같은 계획 수준
  문제만 짚는다.
- **walkthrough (짧게):** 예제 장면에서 촬영 관점이 "이 컷의 샷 크기가
  아직 정해지지 않았다"를 미정으로 표시 → 감독이 확정하거나 그대로 둠.

### 4.3.3 생성 후 — 결과에 들어간 결정 검토하기 (Fig 5)

**핵심 mechanism. 여기가 4.3에서 제일 길다. walkthrough 중심.**

- 스토리보드가 생성되면 세 관점(mise-en-scène, cinematography, editing)이
  화면에 실제로 나타난 연출 결정을 분석한다. narrative는 여기 참여하지
  않는다 — 화면이 정해지기 전에 판단하는 게 그 관점의 자리다 (앞 절).
- 결과를 **관점별 트랙**으로 스토리보드와 가로축을 맞춰 나란히 둔다. 각
  관점이 짚은 문제가 해당 컷(또는 컷 사이) 위치에 표시된다.
  - **왜 트랙인가** — 관점을 탭으로 두면 한 번에 하나만 보여 관점이
    배타적인 것이 된다. 우리 주장은 관점이 서로 얽혀 장면의 의미를
    만든다는 것이므로, 여러 관점이 같은 지점을 짚은 것이 **수직 정렬**로
    보이게 한다. 관계가 별도 설명이 아니라 배치 자체가 된다.
  - 부수 효과: 관점을 사람처럼 캐릭터화하지 않아도 된다. 감독이 겪는 건
    대화 상대가 아니라 그림을 통과하는 렌즈다 (2.x의 "lens not persona"와
    연결).
- 관련된 표시들은 하나의 **issue**로 묶인다. 감독에게는 네 수준의 목록이
  아니라 "검토할 문제 N개"만 제시된다.
  - **설계 결정:** 네 수준(4.4)은 내부적으로 계산하지만 감독에게 나열하지
    않는다. formative에서 참가자가 필요로 한 건 "수정할 문제"였고, 수준을
    다 펼치면 각각 수정 방식이 달라 판단이 어려웠다. (이 근거는 pilot
    관찰. 논문에 넣을지 검토.)
- **issue 하나를 열면:**
  - 세 관점이 이 issue를 어떻게 보는지 — 각자의 입장 (유지 / 다르게 봄 /
    수정 필요).
  - 문제를 짚은 관점의 진단, 그리고 그 판단의 근거 (그 관점의 기준 /
    화면에서 확인한 시각적 근거 / 연결된 영화·연출 이론). 근거는 접혀 있어,
    감독이 원할 때 펼친다.
  - 진단이 근거로 삼은 화면 부분을 **그림 위에 영역으로 표시**한다 —
    근거가 문장뿐 아니라 "화면의 어디"로도 보인다.
  - 아직 이 issue를 안 본 관점은 감독이 불러올 수 있다.
  - **화면만으로 판단할 수 없는 것**은 관점이 감독에게 질문으로 되돌린다.
    감독이 답하면 그 답을 의도에 더해 세 관점을 다시 돌린다. (비대칭 지원:
    보이는 건 판정으로, 안 보이는 건 질문으로 — DR1/DR2.)
  - `그대로 두기`를 포함한 수정 방향 — 고르면 알맞은 수정 도구로 이어진다
    (4.4).
- **기준의 안정성:** 판단 기준은 모델이 매번 자유롭게 만들지 않는다. 각
  관점에 미리 정해 둔 규칙(관점당 4개)에서 고른다. 규칙마다 언제 짚고
  언제 짚지 않는지가 정해져 있고, 관련 이론이 미리 연결돼 있어 진단 뒤에
  임의의 이론을 갖다 붙이지 못한다. (검증 가능성 — reviewer가 물을 것.)

- **cross-lens 관계:** issue 안에서 세 관점의 판단 사이 관계를 세 유형으로
  보여준다.
  - consequence — 한 관점의 결정이 다른 관점의 문제를 만듦 (원인 → 영향)
  - conflict — 서로 다른 관점이 반대되는 수정 방향을 제시
  - agreement — 같은 문제를 서로 다른 영화적 근거로 각자 짚음
  - consequence가 있으면 원인 쪽 관점부터 보라고 권한다. 최종 판단은 감독.
  - 노드 그래프로 시각화 — 어느 관점이 어느 관점과 어떻게 얽혔는지.

- **walkthrough (길게, 예제 장면):**
  1. 감독이 S1–S4를 검토 범위로 잡고 분석을 돌린다.
  2. 미장센 관점이 S3에서 "그래프가 노트북 화면에 붙지 않고 앞에 떠
     보인다"를 짚는다. 근거: 노트북 테두리와 그래프 면의 각도가 안 맞음
     (그림 위에 영역 표시).
  3. issue를 열면 촬영 관점도 "이 렌즈도 고칠 곳을 봄", 편집 관점은
     "다르게 봄". 관계 그래프: 미장센–촬영 agreement, 미장센 → 편집
     consequence.
  4. "함께 보는 문제": S3에서 그래프가 노트북 안 정보로 붙지 않아 하린이
     무엇을 보는지 바로 못 읽게 함.
  5. 촬영 관점이 감독에게 질문: "노트북 안 그래프를 바로 알아보는 게
     우선인지, 하린의 표정이 우선인지." 감독이 답 → 세 관점 재검토.
  6. 감독이 수정 방향을 고른다 → 4.4로.

### 4.3.4 Citation rationale (논문 작성 시 채움)

- 왜 이 네 관점인가 (이론 근거 문헌)
- 왜 스토리보드 단계에서 다룰 수 있는가
- 완전한 taxonomy가 아니라 pragmatic coverage
- 관점들이 결합되어 장면 의미를 만든다는 근거
- 규칙–이론 연결을 어떤 문헌에서 어떤 기준으로 뽑았는지

## 4.4 문제를 그 수준에서 고치기 (DG2)

### 4.4.1 네 수준 (framing)

- 연출 문제는 컷 하나만의 것이 아닐 수 있다 — 컷 안의 요소, 컷 자체의
  구성, 컷과 컷 사이, 장면 전체. formative에서 참가자가 인식한 문제는 이
  네 수준에 걸쳤지만 (F2), 도구의 수정 수단은 대개 개별 패널 재생성에
  머물렀다 (DR2).
- SceneLens는 문제가 어느 수준에 있는지 판단하고 그 수준에 맞는 도구로
  연결한다.
- **수준을 감독에게 목록으로 보여주지 않는다** (4.3.3의 설계 결정). issue의
  수정 방향이 알맞은 도구로 바로 이어진다.
- 수준 → 도구 대응:
  - 컷 안 → 프롬프트 수정 / 그림 위에 덧그리기
  - 컷 → 프레이밍·구도·샷 값 수정
  - 컷 사이 → 이음새 조작
  - 장면 → 장면 기준 수정
- **문제가 보이는 자리와 고치는 자리는 다를 수 있다.** 예: 장면 전체의
  정보 순서 문제는 시퀀스를 통째로 봐야 나오지만 수정은 특정 이음새
  하나에서 한다. (발견과 처분의 분리.)

### 4.4.2 한 컷 수정 (짧게)

- issue에서 수정으로 넘어가면, 그 관점의 수정 지시와 함께 "현재 그림 →
  바뀐 그림" 대조가 나온다. 수정안 2–3개, 각각 짧은 설명. `그대로 두기`와
  `직접 수정`도 있다.
- 수정하는 동안에도 다른 관점의 판단과 관계가 옆에 계속 보인다.

### 4.4.3 컷 사이(이음새)를 편집 대상으로 (Fig 6) — mechanism

- 개별 패널 재생성으로 우회하지 않게, 컷과 컷 **사이**를 직접 다룬다.
- 이음새에서 다루는 것: 두 컷 사이 생략된 사건, 연결 방식, 흐른 시간,
  추가 컷의 필요성 / 연속성 / 정보 흐름 / 리듬.
- 조작: 사이에 컷 넣기 / 합치기 / 나누기 / 순서 바꾸기. 실행 전 함께
  바뀌는 것(컷 수, 사라지는 그림)을 알린다.
- **AI 생성이 이음새 조작에 붙어 있다** — "사이에 넣기"를 누르면 새 패널
  자리가 생기고, 감독이 프롬프트를 쓰거나 AI 제안을 받아 바로 생성한다.
  (구조 조작과 그림 생성이 갈라지지 않는다.)
- **walkthrough:** 4.3의 예제에서 편집 관점이 "S3와 S4 사이에 반응 컷이
  빠졌다"고 진단 → 감독이 이음새를 열어 "사이에 넣기" → AI 제안 중
  "하린이 화면에서 시선을 떼는 짧은 컷" 선택 → 생성.

### 4.4.4 장면 기준을 편집 대상으로 (Fig 7)

- 여러 컷을 가로지르는 것(인물·공간 상태, 배치, 무엇이 언제부터 달라지는지)은
  개별 이미지가 아니라 **구조**로 다룬다. 구조를 바꾸면 그 구간의 패널들이
  앞으로 생성·재생성될 때 공통으로 반영된다.
- 대본에서 뽑은 기준이고, 컷별 배치는 이 기준을 상속하며 달라진 것만 따로
  기록한다.
- 시간 / 인물(공통 기준 + 이 구간의 상태) / 공간(장소 정체 + 고정 소품).

### 4.4.5 요약 문장

- SceneLens는 **문제가 해석 가능해지는 자리**와 **감독이 실제로 고치기로
  한 자리**를 분리한다. 모든 어긋남이 패널 재생성으로 흘러가는 걸 막는다.

## 4.5 의도를 모르는 관객 읽기로 되돌아보기 (DG3, Fig 8)

### 4.5.1 왜 바깥 읽기인가 (framing)

- 감독은 자기 의도를 알기 때문에 화면에 없는 정보도 채워서 본다 (F3, DR3;
  writer-based prose [Flower], 의도 전달 과대평가 [Keysar & Henly]).
- 그래서 "내 의도와 비슷한가"가 아니라 "의도를 모르는 사람이 이 화면만
  보고 그렇게 읽는가"를 확인해야 한다.
- SceneLens는 **감독의 의도를 차단한 읽기**를 되돌려준다. 시스템이 채점하지
  않는다 — 읽기를 보여주고 판단은 감독이 한다 (Schön backtalk, Bordwell
  hypothetical spectator).

### 4.5.2 mechanism

- 읽기에 주는 것: 패널 이미지와 순서. 주지 않는 것: 대본, 컷 라벨, 의도.
- **여러 독립 읽기.** 감독이 읽기 조건 1–3개를 고른다. 갈린 자리를 보려면
  둘 이상. 조건은 페르소나가 아니라 **주목의 차이** — 화면만으로 기본
  이해가 되는가 / 연출 방식(프레이밍·크기·반복) / 컷과 컷의 연결. 감독이
  커스텀 조건도 넣을 수 있다.
  - **왜 여럿인가** — 한 읽기를 "관객의 해석"처럼 권위화하지 않으려고.
    같은 화면이 여러 갈래로 읽힐 수 있음을 보이기 위해.
- **순차 읽기.** 각 조건이 컷마다: 눈에 들어온 것 / 지금 이해 / 앞 컷
  대비 달라진 점 / 지금의 가설 / 아직 궁금한 것. → "이 시점까지 관객이
  무엇을 아는가"를 본다 (관객은 순서대로 읽고, 감독은 전체를 알고 본다는
  차이 — DR3).
- **비교.** 읽기 결과는 스토리보드와 가로축을 맞춘 트랙으로 나온다.
  공통으로 읽힌 부분과 갈린 지점을 나란히 본다. 갈린 자리가 없으면 그렇게
  밝힌다 (침묵을 "문제 없음"으로 오해하지 않게).
  - 핵심은 누가 맞는지가 아니라 **어떤 화면 단서가 다른 해석을 만들었는가**.
- **감독의 재판단.** 갈린 자리에서만 감독이 "이 자리는 어떻게 읽히길
  바라는가"를 적는다. 관객 화면 안에서 고치지 않는다 — 의도를 차단한다는
  원칙을 지키려고 감독의 답을 관객에게 되먹이지 않는다.
- **되돌아오는 연결.** 관객 읽기를 돌리면 연출 검토(4.3.3)의 관점 트랙
  아래에 관객 트랙이 붙는다. 갈린 자리는 거기 표시되고, 감독이 그것을
  누르면 **세 관점이 감독의 답을 전제로 그 지점을 다시 본다.** 즉 DG3에서
  나온 것이 DG1/DG2로 돌아간다 (순환).
- **Difference ≠ Error.** 해석 차이를 자동으로 결함으로 보지 않는다. 그대로
  둘지, 고칠지, 나중으로 미룰지는 감독이 정한다.

### 4.5.3 walkthrough

- 4.3/4.4의 예제 장면(하린)에서: 감독이 "화면만으로 읽기"와 "연출 방식에
  주목" 두 조건으로 읽힘. S3에서 "화면만으로" 조건은 "안 좋은 수치를
  확인한 듯, 걱정", "연출 방식" 조건은 "손을 잡아 대응 쪽으로 무게가
  옮겨간다"로 읽음 → 갈림. 감독이 "발견의 무게를 먼저 읽혔으면 좋겠다"고
  답 → 그 갈림이 연출 트랙에 뜨고, 미장센·촬영이 그 전제로 재검토.

### 4.5.4 Reflective probe, not audience simulation

- 이 1–3개 조건을 실제 인구집단이나 관객을 대표한다고 주장하지 않는다.
- 여러 가능한 읽기를 드러내는 reflective probe로 위치시킨다. 페르소나 기반
  관객 시뮬레이션은 핵심 pipeline이 안정된 뒤의 선택적 확장으로 미룬다.

## 4.6 Implementation (짧은 별도 소절)

- 프론트엔드: 단일 페이지 앱. 백엔드: 이야기 구조화 / 연출 검토 / 관객 읽기
  / 이미지 생성 엔드포인트.
- 모델: (구체 모델명·버전). 관객 읽기는 픽셀이 유일한 근거라 더 큰 모델을
  쓴다. 실패 시 규칙 기반으로 떨어지고 그 사실을 화면에 밝힌다.
- 판단 규칙: 관점당 4개, 총 16개. 각 규칙은 기준·짚을 조건·짚지 않을
  조건과 연결된 이론 유닛을 갖는다.
- 이론 근거: 영화 연출서 N권에서 추출한 유닛 DB. 규칙이 사용할 수 있는
  근거를 그 연결로 제한한다.
- 이미지 생성 모델은 교체 가능. 표현 방식(러프/디테일/실사)에 따라 다른
  화풍 프리셋.
