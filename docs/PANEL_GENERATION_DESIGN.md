## 0. 이 노트가 답하려는 질문

Panels 단계에서 막힌 세 가지.

1. 그림을 생성할 때 **프롬프트는 어디서 오는가**
2. 여기서 **어떤 Agent가 나와야 하는가**
3. 초안은 **대충 생성하는 것인가**

---

## 1. 현재 상태

`handleGeneratePanels`(`src/components/StoryboardView.jsx`)는 프롬프트를 전혀 쓰지 않는다.
`createMockPanelImage(shotIdx, version)`으로 shot 순번에서 SVG를 만들 뿐이다.

**확정된 컷 플랜 데이터가 이미지 생성에 전혀 쓰이지 않는다.** 컷의
`shotSize`가 패널 `cir`로 넘어가긴 하지만(A-1), 그림 자체와는 무관하다.

즉 지금은 줄콘티 → 패널의 연결이 데이터 상으로만 있고 생성에는 닿지 않았다.

## 2. 프롬프트는 결정에서 조립된다

### 2.1 원칙

Spec §22.12는 이미 답을 정해두었다.

> Fixed Decisions are explicit generation constraints.

프롬프트는 사용자가 백지에서 쓰는 것이 아니라 **확정된 결정에서 조립된다.**
줄콘티를 텍스트로 확정한 이유가 여기에 있다 — 컷 분해가 곧 생성 명세다.
별도 프롬프트 창이 주 입력이 된다면 줄콘티 단계가 제 역할을 못 한 것이다.

### 2.2 조립 예시

컷 플랜의 한 행이 프롬프트의 재료가 된다.

```text
Cut 1-2 · 밤 · 관제실 · Bust · 인물: 민호
내용: 생각보다 오래 걸렸네
중요한 것: 발화
        ↓
밤, 지하철 관제실 내부. 민호의 바스트 샷.
앉은 채 돌아보지 않는다. 스토리보드 스케치 스타일.
```

필드 → 프롬프트 자리의 대응(초안):

| 컷 플랜 필드 | 프롬프트에서의 역할 |
|---|---|
| `time` | 시간대·광원 |
| `place` | 공간 |
| `shotSize` | 샷 사이즈 |
| `characters` | 화면에 있어야 할 인물 |
| `content` | 무엇이 일어나는가 |
| `purpose` | 무엇이 읽혀야 하는가 (강조 지점) |

`purpose`는 직접 묘사가 아니라 **무엇을 강조할지**를 정하므로, 구도·시선
유도에 반영되어야 한다. 이 대응은 실제로 돌려보며 조정해야 한다.

### 2.3 그래도 프롬프트 칸은 필요하다

줄콘티로 담기지 않는 정보가 반드시 남는다.

- 조명, 질감, 색감
- 레퍼런스 (예: "복도 장면 느낌으로")
- 그림체 (러프 스케치 / 선화 / 명암)

이것들은 컷 분해의 what-and-when도, 샷 사이즈의 how도 아니다. 표에 컬럼을
더하면 표가 무너진다.

다만 칸의 **성격**이 중요하다.

- 빈 칸에 "알아서 쓰세요"는 안 된다. 줄콘티가 무의미해지고, 초보자는
  파일럿에서 나온 "어디서부터 손대야 할지 감이 안 와서"에 다시 부딪힌다.
- **조립된 프롬프트를 먼저 보여주고, 그 위에 덧붙이는** 형태여야 한다.

```text
이 컷의 프롬프트                                    [편집]
┌──────────────────────────────────────────────┐
│ 밤, 지하철 관제실 내부. 민호의 바스트 샷.        │  ← 컷에서 자동
│ 앉은 채 돌아보지 않는다.                        │
├──────────────────────────────────────────────┤
│ + 추가 지시                                    │  ← 사용자가 덧붙임
│   차가운 형광등, 거친 연필 스케치               │
└──────────────────────────────────────────────┘
```

두 영역을 분리해 두면 provenance도 자연히 갈린다. 자동 조립분은 AI,
추가 지시는 User다. 사용자가 자동 조립분을 직접 고치면 그 컷의 해당
결정이 User로 바뀐다(Spec §8.3).

**열어둔 질문**: 추가 지시를 컷마다 둘지, 장면 전체에 한 번 둘지.
조명·그림체는 보통 장면 전체에 걸리므로 둘 다 필요할 수 있다.

## 3. Agent는 새로 나오지 않는다

### 3.1 UI에 Agent는 Narrative 하나뿐

Spec §9.1이 명시한다.

> In the product UI, only Narrative is presented as an Agent (…). Mise-en-scène,
> Cinematography, and Editing are presented as Creative Lenses (…) the user
> should not have to manage four conversational personas.

Panels 단계에서 새 대화형 Agent를 띄우는 것은 이 결정에 어긋난다.
"관리해야 할 네 개의 대화 상대"가 정확히 피하려던 것이다.

### 3.2 하위 렌즈는 Option card로 나타난다

대신 하위 렌즈는 **선택지**로 등장한다(Spec §15).

```text
컷 1-2 · 카메라 거리
현재: Bust          AI · Tentative

  A. Close-Up
     효과: 표정에 집중
     비용: 공간 단서가 사라짐

  B. Wide
     효과: 두 사람의 거리가 드러남
     비용: 표정이 약해짐
```

대화 기록이 아니라 효과·비용이 붙은 카드다. Spec §16의 cross-agent
response(Supports / Trade-off / Narrative check)도 자유 대화가 아니라
선택된 Option에 대한 짧은 구조화된 반응이다.

### 3.3 따라서 Panels 단계의 오른쪽

Script 단계의 Narrative rail이 그대로 남아 있을 자리가 아니다.
**선택된 컷/패널의 Option 패널**로 바뀌는 것이 맞다.

Narrative는 사라지지 않고, 하위 선택이 서사에 영향을 줄 때
`Narrative check`로 올라온다(Spec §9.7).

## 4. "초안은 대충 생성하는 것인가"

### 4.1 대충이 아니라 "확정 안 된 것이 확정 안 된 것처럼 보여야" 한다

파일럿에서 수정하지 않은 요소가 세 갈래로 갈렸다.

- 진짜 만족
- placeholder로 수용
- **인지하지 못한 AI-filled assumption**

매끈하게 완성된 이미지를 주면 이 셋이 구분되지 않는다. 세 번째가
그대로 후속 제작에 넘어간다 — false finality.

> 2026-08-04 `design_goal.md` 재구성 후 DG 번호가 바뀌었다. 이 절이 다루는
> 것은 신 **DG1 P3 (이미지가 책임질 범위를 선언한다)** 이다. 새 프레임의
> 용어로는, 화면에 없는 것이 **결손**인지 **위임**인지 구분하는 문제다.

### 4.2 상태별 처리

| 상태 | 프롬프트 | 화면 |
|---|---|---|
| Fixed | 명시적 제약으로 반영. 재생성해도 유지 | 확정 표시 |
| Tentative | 반영하되 구속력 없음 | **비구속임이 보여야 함** |
| Open | 의도적으로 열어둔 부분. 모델이 채우되 | 열려 있음이 보여야 함 |

Spec §17.5가 이 지점을 짚는다.

> An image model may need to render a concrete visual detail even when its
> Decision is Open or Tentative. Rendering a detail does not change its
> commitment status. The interface must continue to show that the visible
> implementation is nonbinding.

이미지 모델은 방의 더러움 정도를 어떻게든 정해야 한다. 그것이 사용자
결정으로 둔갑하면 안 된다.

### 4.3 미정: 비구속을 어떻게 보일 것인가

Spec에도 정해져 있지 않다. 후보:

- **러프한 렌더링** — Tentative 요소를 덜 그려진 상태로. 직관적이지만
  이미지 모델에 부분적 fidelity를 지시하기 어렵다
- **뱃지/오버레이** — 패널 위에 "이 컷의 배경은 미검토" 표시. 구현은
  쉽지만 이미지 자체는 여전히 매끈하다
- **결정 목록 병치** — 패널 옆에 그 패널의 Tentative 결정을 나열.
  DG1 P1(요구 역할 외부화)과 직결되고 구현 가능하나, 이미지에서 눈을
  떼게 만든다

세 번째가 가장 현실적으로 보이나, 첫 번째가 개념적으로는 가장 맞다.
**실제로 생성해보고 판단해야 한다.**

**2026-08-04 갱신.** 이 미결 질문은 DG1 P3의 [이미지에서 확정 / 방향만
표시 / 후속 공정에 완전 위임] 축과 같은 문제였다. P3는 나아가 "확정하지
않는 요소는 이미지 밖 채널(액팅 메모, 움직임 화살표, 카메라 이동,
타임코드)에 기록한다"는 답을 제시한다 — 위 세 후보 중 두 번째·세 번째의
구체화에 해당한다. P3 구현이 이 절의 후속이다.

## 5. 다음 단계 제안

한 번에 다 만들지 않는다.

1. **컷 → 프롬프트 조립을 mock으로 붙인다.** 실제로 어떤 문장이
   나오는지 눈으로 본다. §2.2의 필드 대응이 맞는지는 이걸 봐야 안다
2. 조립된 프롬프트 + 추가 지시 칸 UI
3. 실제 이미지 생성 API 연결 (한 패널 먼저)
4. 상태별 표시 (§4.3에서 하나 골라)
5. Option card로 오른쪽 패널 전환

1번을 먼저 하는 이유: 프롬프트가 실제로 어떻게 생겼는지 봐야 2·4번의
판단이 선다.

## 6. 열어둔 질문

- 추가 지시를 컷 단위로 둘지, 장면 단위로 둘지, 둘 다일지
- `purpose`를 프롬프트에 어떻게 반영할지 (강조는 묘사로 번역하기 어렵다)
- 인접 컷의 일관성 — 같은 인물·공간이 컷마다 달라 보이는 문제
  (레퍼런스 이미지 고정이 필요할 수 있다)
- Fixed 결정이 재생성에서 실제로 유지되는지 어떻게 검증할지
- 비구속 표시 방식 (§4.3)
- 사용자가 조립된 프롬프트를 직접 고쳤을 때, 원래 컷 데이터와 어긋나면
  무엇을 진실로 볼지
