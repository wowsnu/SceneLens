## 1. 해결하려는 문제

기존 서사 렌즈의 약점은 **"상위 층에서 컷 분해·순서를 담당한다"가 시스템 설계상의 추상적 구분**이었다는 점이다.

Spec의 2층 구조(Narrative 상위 / Mise-en-scène·Cinematography·Editing 하위)는 내부적으로는 일관되지만, "왜 하필 이렇게 나눴는가"에 대한 답이 연구자의 설계 편의에서 나온다. CHI 리뷰어에게 이건 약한 정당화다.

또한 `system.txt` 245행에 남긴 자기 비판이 정확히 이 지점을 가리킨다.

> DG들이 일반적이다. 애매한 것 같다. 스토리보드에 좀 더 맞닿아야 있어 보일 필요가 있음. 도메인에게 잘 맞게 붙여보는 작업이 있어야 함.

줄콘티 프레이밍은 이 요구에 대한 직접적인 답이다. 2층 구조가 **연구자가 발명한 추상이 아니라 현업 관행의 계산적 구현**이 된다.

---

## 2. 줄콘티란 무엇인가

### 2.1 정의

줄콘티(글콘티)는 **콘티(continuity)의 글 버전**이다. 그림 없이 텍스트로만 컷을 분해하고 각 컷의 내용·순서·촬영 방식을 기술한다.

- 그림콘티(스토리보드) **이전 단계**에 위치한다.
- 시나리오가 완성된 뒤, 줄콘티 → 콘티 → 스토리보드 순으로 진행된다.
- 감독의 연출 의도를 스태프에게 전달하고, 컷 전환과 카메라 이동을 사전에 계획하는 문서다.

작성 예시(필름메이커스/커뮤니티 자료 인용):

> 미숙이의 방 책상 쪽을 비추는 카메라 서서히 달리인을 해서 책상 위의 손목시계를 클로즈업으로 비춘다. 초침이 멈춰있다가 갑자기 째깍하며 움직이기 시작한다.

### 2.2 인접 문서와의 구분

현업에서 사전제작 문서는 역할이 갈린다.

| 문서 | 역할 |
|---|---|
| 씬리스트 | 전체 씬의 개요. 촬영 흐름을 빠르게 파악 |
| 씬 브레이크다운 | 각 씬의 촬영 준비 사항(배우·의상·소품·조명) |
| **줄콘티(글콘티)** | **연출적 디테일. 컷 분해, 컷 전환, 카메라 움직임, 배우 동작을 텍스트로 기술** |
| 그림콘티(스토리보드) | 위 결정을 시각화한 패널 |

SceneLens가 대응하는 것은 **줄콘티 → 그림콘티** 구간이다.

### 2.3 영어권 대응물

영어권에서 가장 가까운 것은 **shot list**다. 감독·촬영감독·조감독이 사전제작 단계에서 작성하는 문서로, 촬영할 모든 셋업을 글로 기술한다. 관련 문헌의 공통된 입장은 shot list와 storyboard가 경쟁 관계가 아니라 **상보적**이며, shot list가 storyboard의 비전이 실제로 어떻게 촬영되는지를 규정한다는 것이다.

논문에서는 줄콘티를 primary 용어로 쓰되, 국제 독자를 위해 shot list를 대응어로 병기하는 편이 안전하다. 다만 shot list는 촬영 스케줄링 문서 성격이 강해 줄콘티보다 연출 의도 기술의 비중이 낮으므로, 완전한 동의어로 다루지는 않는다.

## 3. Formative 근거 (지함 세션)

이 프레이밍의 정당화는 전적으로 formative 데이터에서 나온다.

### 3.1 워크플로우 진술 (핵심 근거)

지함이 설명한 현업 순서:

```
감독이 대본을 쓴다
  → 촬영감독과 함께 줄콘티를 짠다
     (이 신은 풀샷 하나, 바스트 둘, 클로즈업 하나 — 텍스트로 합의)
  → 그다음에 그림 콘티
```

여기서 두 가지가 동시에 확인된다.

1. **그림 그리기 전에 컷 분해를 텍스트로 확정하는 중간 단계가 실재한다.**
2. **그 단계가 감독-촬영감독의 협상으로 이루어진다.** 이는 서사 렌즈가 제안하고 사용자가 조정하는 negotiable 구조와 정확히 같은 모양이다.

### 3.2 이를 지지하는 다른 발화

- **"전체 스토리를 넣으면 정확도가 떨어지니 씬 단위로 쪼개 입력하겠다"**
  → 텍스트 수준에서 먼저 구조를 잡으려는 요구. 일괄 생성에 대한 실무자의 불신.
- **"구도가 생각과 다르면 제일 먼저 고친다"**
  → 그림으로 가기 전에 확정됐어야 할 결정이 그림에서야 드러난다는 증거. 줄콘티 단계가 없어서 생기는 비용.

### 3.3 초보자 데이터와의 연결

파일럿 참가자의 **"어디서부터 손대야 할지 감이 안 와서"**는 이미지 수준 수정의 진입 장벽을 보여준다. 줄콘티는 이 문제에 대한 구조적 답이다 — 텍스트에서는 "컷 3개? 4개로 늘려줘"가 쉽다.

즉 **전문가 워크플로우 관찰(지함)과 초보자 실패 관찰(파일럿)이 같은 설계 결정으로 수렴한다.** 이게 이 프레이밍의 가장 강한 점이다.

## 4. 왜 인터랙션 설계로도 말이 되는가

기존 도구들의 문제는 **"스크립트 → 그림 일괄 생성"으로 컷 분해 결정이 암묵 처리된다**는 것이었다(related work cluster 2).

줄콘티 단계를 명시적으로 끼워넣으면:

```
스크립트
  → 서사 렌즈가 줄콘티 제안
     (텍스트: 컷 몇 개, 각 컷에 무엇을, 어떤 순서로)
  → 사용자가 여기서 검토·수정          ← 텍스트라 수정 비용이 싸다
  → 확정된 줄콘티 기반으로 하위 렌즈들이 그림 실현
```

### DG와의 맞물림

> DG 번호는 2026-08-04 `design_goal.md` 재구성 기준이다 (구 DG1–4 → 신 DG1–3).

- **DG1 surface (P1·P2)**: 줄콘티는 컷 수·내용·순서라는 결정을 그림에 섞이기 전에 텍스트로 노출한다. AI-filled decision이 이미지 안에 숨는 것을 구조적으로 막는다. 컷별 요구 역할을 밖에 두는 P1의 부착 지점이 곧 줄콘티 항목이다.
- **DG1 P3 (이미지 책임 범위 선언)**: 줄콘티 항목이 [이미지에서 확정 / 방향만 표시 / 후속 공정에 완전 위임]의 자연스러운 부착 지점이 된다. 그림 패널보다 훨씬 명확한 결정 단위다.
- **DG2 P1 (이음새 편집)**: 감독-촬영감독의 줄콘티 협상 — 컷을 나누고 합치는 논의 — 이 곧 병합·분할·삽입의 현업 대응물이다.

**결정을 사용자가 만질 수 있는 형태로 먼저 노출한다** — 이게 SceneLens의 핵심 명제이고, 줄콘티는 그것의 도메인 고유한 구현체다.

## 5. 경계 설정 (반드시 명시할 것)

### 5.1 문제

줄콘티는 현업 용어라 **촬영 지시(삼각대, 풀샷, 달리인)까지 포함하는 개념**이다. 위 인용 예시에도 "달리인", "클로즈업"이 들어 있고, 지함의 설명("풀샷 하나, 바스트 둘")도 샷 사이즈를 포함한다.

서사 렌즈가 줄콘티를 그대로 구현하면 **샷 사이즈까지 정해버려 촬영 렌즈와 경계가 뭉개진다.**

### 5.2 채택할 경계

논문에서는 다음과 같이 명시한다.

> 줄콘티에서 영감을 받되, 서사 렌즈는 **what-and-when**(컷의 존재·내용·순서)까지만 담당하고, **how**(샷 사이즈·앵글·프레이밍)는 하위 렌즈의 몫이다.

| | 서사 렌즈 (줄콘티 층) | 하위 렌즈 |
|---|---|---|
| 담당 | 컷의 존재, 각 컷의 내용, 컷의 순서, 정보 공개 시점 | 샷 사이즈, 앵글, 프레이밍, 배치, 전환 방식 |
| 질문 | 무엇을 언제 보여주는가 | 그것을 어떻게 보여주는가 |

이 경계는 Spec §9.6(Narrative와 Editing 경계)의 기존 서술과 일관된다. Narrative는 "무엇이 알려져야 하는가 / 언제 공개되는가", Editing은 "몇 개의 컷으로 / 어떤 리듬으로"를 답한다.

### 5.3 부수 효과

이 작업은 최근 세션에서 확인된 **지함의 "서사 = 스토리 내용" 오독** 문제에 대한 대응과 같은 작업이다. 렌즈 경계를 명시해야 한다는 요구가 두 경로에서 동시에 나왔다.

주의: 줄콘티를 "서사"라고 부르면 오독이 재발할 수 있다. UI 레이블은 `Narrative`보다 컷 분해를 직접 가리키는 표현(예: `Cut plan`, `줄콘티`)을 검토한다.

## 6. Formative 질문지에 대한 함의

**질문지는 바꾸지 않는다.** 이건 시스템 설계 변경이고, v3 질문지 그대로 진행한다.

오히려 기존 질문의 의미가 선명해진다.

- **"컷 수·순서를 그대로 받아들였나"** → 줄콘티 단계의 필요성을 재는 질문이 된다. 그대로 받아들였다면 그건 만족이 아니라 컷 분해가 암묵 처리됐다는 신호일 수 있다(= 인지하지 못한 AI-filled assumption).
- **"한 컷을 수정할 때 그 컷만 보고 고쳤나, 앞뒤 흐름까지 보고 고쳤나"**(RQ2) → 줄콘티 층의 결정과 패널 층의 결정을 참가자가 구분하는지 재는 질문이 된다.

## 7. v3 구현으로의 반영

현재 Narrative rail(`src/components/StoryboardView.jsx:810-942`)은 두 가지 작업만 제공한다.

- `Revise Beat` — 현재 Beat의 inline 제안
- `Create Script` — 아이디어에서 전체 Script Draft Mock 생성

**둘 다 대본(텍스트) 층에서 대본(텍스트)으로 가는 작업이고, 컷 분해를 다루지 않는다.** 대본에서 패널로 넘어가는 순간 컷 수·순서가 암묵적으로 결정된다 — 정확히 지금 없애려는 문제다.

### 제안하는 세 번째 작업

Narrative rail에 `Propose Cut Plan`(줄콘티 제안)을 추가한다.

```
Ask Narrative
  [ Revise Beat ] [ Create Script ] [ Propose Cut Plan ]
```

산출물은 패널이 아니라 **텍스트 컷 리스트**다. 각 항목의 필드(서사 렌즈 담당 범위로 한정):

```text
CutPlanItem
  id
  order          컷 순서
  beatId         소속 Beat (screenplay element ID 참조)
  content        이 컷에서 무엇이 일어나는가 (what)
  reveals        이 컷이 새로 공개하는 정보 (when)
  purpose        이 컷이 존재하는 이유
  status         Fixed / Tentative / Open
  provenance     User / AI
```

의도적으로 **넣지 않는** 필드: `shotSize`, `angle`, `framing`, `cameraMovement`. 이건 하위 렌즈가 채운다(§5.2).

### 사용자 조작

텍스트 층에서 싸게 수정할 수 있어야 한다.

- 컷 추가 / 삭제
- 컷 순서 변경
- 컷 분할 / 병합 (기존 Beat Split/Merge 언어 재사용)
- 항목별 `Accept / Dismiss`
- 항목별 상태 지정 (Fixed / Tentative / Open)

### 흐름상의 위치

```
Edit Script
  → Apply to Storyboard
  → Propose Cut Plan          ← 신규. 텍스트 줄콘티
  → 사용자 검토·수정
  → Accept Cut Plan
  → 확정된 컷마다 Blank / Draw / Generate / Import
  → 초기 hybrid Board (Round 0)
```

이는 Spec §10.6의 `Propose Beat & Cut Structure → Accept Scaffold` 흐름을 **줄콘티라는 이름과 현업 근거를 가진 단계로 구체화**한 것이다. Spec의 scaffold 개념을 대체하는 게 아니라, 그것에 도메인 정체성과 사용자가 만질 수 있는 데이터 구조를 부여한다.

### 구현 순서 메모

Spec §25의 first vertical slice와 충돌하지 않는다. 오히려 slice를 더 구체화한다. Cut Plan 항목은 Decision 모델이 붙는 첫 대상으로 삼기 좋다 — 이미 결정 단위로 분절돼 있고, 상태·출처를 붙일 자리가 명확하며, 이미지 생성 없이 Fixed/Tentative/Open 전체 루프를 검증할 수 있다.

## 8. 논문에 쓸 때

System 섹션 도입부 형태:

> 영화 사전제작에는 그림 콘티에 앞서 컷 분해를 텍스트로 확정하는 단계가 존재한다. 한국 현장에서는 이를 줄콘티라 부르며, 감독과 촬영감독이 각 신을 몇 개의 컷으로 나눌지 텍스트 수준에서 합의한다. 우리의 formative 세션에서 전문 감독은 이 단계를 대본 집필과 그림 콘티 사이의 필수 협상 과정으로 기술했다. SceneLens의 서사 렌즈는 이 관행의 계산적 구현이다. 다만 현업의 줄콘티가 샷 사이즈와 카메라 움직임까지 포함하는 것과 달리, 우리는 서사 렌즈의 범위를 컷의 존재·내용·순서(what and when)로 한정하고 샷 사이즈·앵글(how)은 하위 렌즈에 위임하여 렌즈 간 경계를 유지한다.

리뷰어의 "왜 이렇게 나눴는가"에 대한 답: **전문가들이 원래 이렇게 나눈다. 그 근거는 우리 formative 데이터에 있다.**

## 9. 열어둔 질문

- 줄콘티 항목과 Beat의 관계 — 1:N인가, 별도 층인가. (Spec §10.7의 Beat/Cut 구분과 정합적으로 정리 필요)
- UI 레이블을 `Narrative`로 유지할지, 컷 분해를 직접 가리키는 표현으로 바꿀지 (§5.3)
- 사용자가 줄콘티 단계를 건너뛰고 바로 패널로 갈 수 있어야 하는가 — 강제하면 초보자에게 부담, 선택하면 암묵 처리 문제가 남는다
- 줄콘티 항목과 패널의 매핑이 이후 라운드에서 깨질 때(패널 추가·삭제) 어떻게 유지할지
- 논문에서 shot list를 대응어로 병기할지, 줄콘티만 쓰고 각주로 설명할지
